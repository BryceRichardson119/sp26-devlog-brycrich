While completing the ICEX independently, I encountered an issue with the duplicate-rating behavior. When testing the endpoint POST /jokes/7/ratings twice with the same user, both requests returned 201 Created, when the second request should have failed. This indicated that duplicate ratings were being allowed, violating the intended constraint. To diagnose the issue, I first confirmed the behavior using curl and observed that no error output (such as an IntegrityError) appeared in the logs. I then inspected models/rating.py and found that the model was missing a UniqueConstraint('user_id', 'joke_id'), which is required to prevent duplicate entries at the database level.

To resolve the issue, I added the UniqueConstraint to the model as a config change, then generated and applied a new migration to update the database schema. After restarting the server, I reran the same curl test. The first POST request still returned 201, but the second now raised an IntegrityError, which I handled in the route to return a 409 Conflict response instead. This confirmed that the constraint was working correctly and enforcing idempotency as intended. The key artifact for this fix was the config change adding UniqueConstraint('user_id', 'joke_id') in models/rating.py, along with the observed change in endpoint behavior after applying the migration.
